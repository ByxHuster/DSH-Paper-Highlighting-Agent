# 方案汇报 02 —— Paper Highlight Agent：系统主流程与自适应画像架构

## 概述

**Paper Highlight Agent** 是一款采用 **Human-in-the-loop（人机协同）** 范式的论文多色高亮辅助系统。系统由 Agent 提出候选标注，用户在 GUI 界面进行审查与微调，Agent 进而从用户的决策日志中持续学习标注偏好，实现“越用越懂你”的个性化演进。

核心架构分为两大模块：
1. **协同工作主流程**：涵盖全局规划、节级增量交互与全局收尾的标准链路。
2. **个性化画像系统（Highlight Profile）**：支持自适应学习且具备严格安全隔离的偏好管理机制。

---

## 一、主协同工作流程

系统采用 **“前置粗规划 + 节级细交互 + 终态全局收尾”** 的工作流，避免“一次性全篇标注导致用户全盘推翻重来”的体验痛点。

### 1. 核心状态机与数据流

```
【阶段一：离线解析与全局规划】
  PDF ──① MinerU 解析──> 归一化 (paper.md / anchors.json) 
                         │
                         ▼
        ② 全局通读 (paper-hl-global-read) ──> 章节策略计划 (plan)

【阶段二：节级交互循环（Section-by-Section Loop）】
  ┌─────────────────────────────────────────────────────────────┐
  │  ③ 候选生成 (paper-hl-propose)                             │
  │     └─ 结合画像与上下文，生成当前节 proposed spans ──> 挂起等待 │
  │                                                             │
  │  ④ 专家审查（用户 GUI 操作）                                 │
  │     └─ 接受 / 否决 / 改色 / 调范围 ──> 写入 append-only 日志 │
  │                                                             │
  │  ⑤ 差异反思 (paper-hl-reflect)                             │
  │     └─ 比对 proposed vs final ──> 输出 reflections.json 提案│
  │                                                             │
  │  ⑥ 画像确认 (confirm_proposal)                              │
  │     └─ 用户单向确认 ──> Host 进程受控合入 Profile 字典        │
  └───────────────────────────────┬─────────────────────────────┘
                                  │ 全部章节审查完毕
                                  ▼
【阶段三：全局收尾】
  ⑦ 论文级反思 (reflect_paper) ──> 汇总模式 + 增补领域发展线 (field-map)
```

---

### 2. 阶段执行要点

| 阶段 | 步骤与组件 | 核心行为与输出 | 设计考量 / 约束 |
| :--- | :--- | :--- | :--- |
| **准备** | **① 多模态解析**<br>`mineru.js`<br>`normalize.js` | 经 MinerU 云端 API 提取后归一化，保留正文、行内/行间公式、表格、图表说明（caption）与图片栅格；输出 `paper.md` 与 `anchors.json`。 | 为高亮提供精确的文本锚点（Anchor），建立纯净的基础语料。 |
| **规划** | **② 全局计划先行**<br>`global-read` | 通读全文结构，输出**章节级规划（Plan）**：定义各节预期色系分布（`expected_colors`）、目标密度（`density_hint`）及跳过建议（`skip`）。 | 用户可前置介入校准预期，防止 Agent 盲目标注带来的高成本返工。 |
| **协作循环** | **③ 节级增量提出**<br>`propose` | **一次只处理当前节**。读取该节正文并生成候选标注（颜色、理由 `rationale`、文本粒度），写入 `status: proposed`，随即**挂起等待**。 | 控制单次审查心智负担，支持增量上下文演进。 |
| | **④ 人机对齐审查**<br>用户在 GUI 介入 | 用户对高亮进行“接受 / 否决 / 改色 / 微调范围 / 添加备注”。所有动作以 **Append-only** 形式记录在 span 的 `decisions[]` 数组中。 | 保证操作日志可审计、可回溯，为反思引擎提供结构化学习依据。 |
| | **⑤ 差异提取与反思**<br>`reflect` | 对比当前节的 `proposed` 与 `final` 状态，执行差异分析（改色规律、删除误报模式、粒度倾向），生成**画像更新提案（`reflections.json`）**。 | Agent 仅拥有“提案权”，无直接“落盘权”。 |
| | **⑥ 提案受控合并**<br>用户 + Host 进程 | 用户在 GUI 提案面板勾选并确认建议，由 Host 主机进程执行合并，完成单次偏好更新。 | **严格防污染机制**：隔绝模型幻觉导致的偏好漂移。 |
| **收尾** | **⑦ 终态全篇复盘**<br>`reflect_paper` | 全文审阅完成后，汇总整篇论文的标注统计规律，沉淀该文核心经验，并按需增补/串联该研究方向的领域发展图谱（field-map）。 | 实现跨论文、跨领域的长期记忆与知识网络构建。 |

### 3. 展示性内容治理策略（v0.7.0）

为避免视觉渲染冲突与无效标注：
* **界限划分**：表格和图片主体属于“真实渲染的纯展示性元素”，**严禁参与高亮选取**。
* **双层拦截机制**：
  1. **技能提示层**：`propose` 与 `plan` 技能显式忽略展示性块体，仅将其视作阅读理解的上下文支撑；**图/表说明（`*_caption`）允许作为正文正常高亮**。
  2. **Schema 校验层**：校验规则对所有试图跨入展示块范围的 spans 实施硬兜底，自动过滤或拒绝入库。

## 二、画像系统（Highlight Profile）

画像系统位于 `highlight-profile/` 目录，是 Agent 实现持续个性化对齐的核心机制，负责将用户离散的历史决策收敛为通用、稳定的高亮规则。

### 1. 四层分层架构

画像系统解耦为四层独立维护的文件，兼顾直观性、灵活性与统计学稳定性：

```
┌────────────────────────────────────────────────────────┐
│ L1 颜色语义层 (colors.yml)                             │
│ └─ 基础定义：标注颜色与学术价值映射（如 red=核心贡献）  │
├────────────────────────────────────────────────────────┤
│ L2 偏好规则层 (rules.json)                             │
│ └─ 结构化偏好：密度基线、切词粒度、置信度隔离机制       │
├────────────────────────────────────────────────────────┤
│ L3 上下文示例库 (exemplars.json)                       │
│ └─ 典型案例检索源：记录特定主张与用户的干预倾向         │
├────────────────────────────────────────────────────────┤
│ L4 偏好置信度统计 (stats.json)                         │
│ └─ 统计量化指标：跨篇章/跨维度的长期认可率评估          │
└────────────────────────────────────────────────────────┘
```

* **L1 颜色语义层 (`colors.yml`)**：配置语义映射。
  * *默认基线*：`red`（核心贡献）、`yellow`（关键定义/方法）、`blue`（局限/风险）、`green`（启发/借鉴）、`purple`（存疑/待深挖）。支持用户自定义语义。
* **L2 偏好规则层 (`rules.json`)**：明确行为准则。
  * 涵盖密度基线（如单节 3–5 处）、切片粒度（句子级 vs 短语级）。
  * **置信度隔离机制**：初次反思得到的边缘规律以 `enabled: false` 形式作为“禁用候选”归档，唯有积累多次正向证据后方予激活。
* **L3 上下文示例库 (`exemplars.json`)**：模式参考集合。
  * 记录“原始建议 + 用户决策倾向”的成对样本。作为 Agent 推演上下文时的参考信号（Soft Signal），不直接篡改显式规则。
* **L4 偏好统计层 (`stats.json`)**：稳定性度量底座。
  * 维护诸如“标注 3 篇论文 · 偏好认可率 78%”等长期指标，量化用户偏好收敛程度。

### 2. 闭环自适应学习机制（防污染设计）

为防止 Agent 在学习过程中因一次异常决策产生偏好漂移，系统设计了闭环隔离路径：

```
用户交互审查 (GUI decisions[] 日志)
      │
      ▼
reflect 差分提取 (对比 proposed 与 final)
      │
      ▼
生成 reflections.json 阶段性提案
      │ (规则增补 / 示例入库 / 统计步进)
      ▼
GUI 偏好确认面板 ◄─── 用户显式介入审阅（支持单条拒绝/通过）
      │
      ▼ (confirm_proposal 触发)
Host 进程执行幂等合并 ──> 最终写入四层 Profile
```

#### 关键防污染原则：
1. **提案制（Proposal-only）**：Agent **永远不具备直接写入画像的权限**，其反思结果仅作为待审批项展示在面板中，确保系统自学习透明可控。
2. **操作幂等与单向性**：提案确认操作是 Append-only 机制，已消费的提案内嵌唯一校验码，规避重放导致的重复合并。
3. **软信号与硬规则解耦**：示例（L3）仅充当 Prompt 中的少样本参考（Few-shot prompt），只有高频、高一致性的行为才会经确认提炼至硬规则（L2）。
4. **冷启动与增量热重载**：
   - *冷启动*：无画像历史时，系统回退至内置最佳实践基准。
   - *增量热重载*：在执行 `propose` 任务前，Agent 会**实时拉取当前最新的画像快照**，确保上一节刚确认的偏好更新立即可在下一节生效。

---

### 3. 画像驱动决策的优先级体系

在执行 `propose` 为某节生成候选时，Agent 严格遵循以下决策优先级（从高到低）：

$$\text{已确认画像规则 (Profile L2)} > \text{全局通读期规划 (Plan)} > \text{系统内置默认基准 (Default)}$$

* **颜色决策**：优先采纳 L1 设定的业务语义；若被用户重写，则以画像覆盖系统内置语义。
* **密度与粒度**：优先采纳 L2 中处于 `enabled: true` 状态的规则；若无显式规则，采用该节 Plan 阶段由大模型预测的 `density_hint`；均无则回退至基准（每节 3–5 处）。
* **保守/进取倾向调节**：
  * **高认可率（L4 偏好稳定）**：Agent 提升自信度，深度倾向于按 L3 示例库匹配模式进行泛化。
  * **低认可率 / 样本不足（偏好未收敛）**：Agent 采取防御性策略，收缩高亮密度，严格依托基线保守提议，降低人机对抗成本。
